# 开发与变更记录规范

## 目的

让项目中的每一次修改都能回答以下问题：

1. 为什么要改？
2. 具体改了什么？
3. 如何证明修改有效？
4. 带来了什么量化或可观察的效果？
5. 出现问题时如何回滚？

## 变更类型与编号

| 前缀 | 使用场景 | 示例 |
|---|---|---|
| `FEAT` | 新功能 | `FEAT-001` 文档上传与解析 |
| `FIX` | 缺陷修复 | `FIX-001` 修复重复消费造成的重复索引 |
| `PERF` | 性能或成本优化 | `PERF-001` 批量 Embedding 降低入库耗时 |
| `ARCH` | 架构与工程调整 | `ARCH-001` 建立模块边界和记录规范 |
| `SEC` | 安全与权限 | `SEC-001` 检索层强制租户过滤 |
| `EVAL` | 评测与实验 | `EVAL-001` 比较三种检索策略 |
| `DOC` | 纯文档修改 | `DOC-001` 补充部署说明 |

编号在各类型内递增且不复用。若一次修改同时涉及多个方面，按主要目标确定类型，并在影响范围中说明其他方面。

## 标准工作流

### 修改前

1. 在 `CHANGELOG.md` 创建状态为“计划中”或“进行中”的记录。
2. 描述问题现象、复现步骤或能力缺口。
3. 尽可能记录修改前基线：失败用例、日志、Trace、Recall、延迟、吞吐或成本。
4. 确定验收标准，确保“完成”可以被验证。

### 修改中

1. 在记录中维护关键设计决定和影响模块。
2. 新增或修改自动化测试，避免只靠手工验证。
3. 如实现偏离原方案，记录偏离原因，而不是覆盖历史事实。

### 修改后

1. 执行与风险相匹配的单元测试、集成测试、评测或压测。
2. 用同样的数据集、环境、预热方式和统计口径比较修改前后结果。
3. 更新状态、验证结果、实际效果、遗留问题和回滚方式。
4. Git 提交信息包含变更编号，并在提交前检查 `CHANGELOG.md` 已同步更新。

## 效果记录要求

效果必须来自证据，可以是：

- 功能效果：原失败用例通过、接口响应符合验收条件。
- 质量效果：Recall@5、MRR@10、Faithfulness、拒答 F1 或工具选择准确率变化。
- 性能效果：P50/P95/P99、吞吐量、内存、CPU 或索引耗时变化。
- 成本效果：平均输入/输出 Token、缓存命中率或单请求估算成本变化。
- 稳定性效果：错误率、重试率、任务成功率或恢复时间变化。

禁止使用没有测试依据的“显著提升”“大幅优化”。没有基线时写“未建立基线”，尚未完成验证时写“待验证”。

## 建议的证据存放位置

```text
docs/
├─ changes/          # 较复杂变更的详细设计或复盘
├─ decisions/        # ADR 架构决策记录
├─ evaluations/      # RAG/Agent 评测报告
└─ benchmarks/       # 压测环境、脚本说明和结果
```

小修改直接记录在 `CHANGELOG.md`；需要多轮实验、涉及重要取舍或存在生产风险的修改，再增加独立文档并从变更记录链接过去。

## Git 提交规范

```text
feat(rag): FEAT-003 增加 BM25 与向量混合检索
fix(ingestion): FIX-002 修复文档重复消费
perf(agent): PERF-001 缓存工具描述减少 Token 消耗
test(eval): EVAL-002 增加无答案问题评测集
docs(architecture): ARCH-003 记录模型降级方案
```

一个提交尽量只对应一个主要变更编号。若同一变更需要多个提交，所有相关提交都保留相同编号。

## Code Review 检查项

- 是否能明确复现原问题或说明能力缺口？
- 是否说明关键修改及影响范围？
- 是否有自动化验证或合理的手工验证记录？
- 前后指标是否使用相同口径？
- 是否考虑权限、数据兼容、并发、失败重试和可观测性？
- 是否写清遗留问题及回滚方案？
- `CHANGELOG.md` 是否已更新？
